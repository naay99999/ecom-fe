# Repository Guidelines

## Project Structure & Module Organization

This is a Vite-powered React application. Application code lives in `src/`:

- `pages/` contains route-level screens (for example, `ProductsDetailPage.jsx`).
- `layouts/` provides shared route shells such as `RootLayout.jsx` and `AccountLayout.jsx`.
- `features/` groups domain-specific UI and logic (`auth/`, `cart/`, `products/`).
- `components/ui/` contains reusable shadcn-style primitives; put cross-feature UI here.
- `lib/` contains shared utilities, while `styles/globals.css` holds global styles.
- Static files belong in `public/`; source-imported assets belong in `src/assets/`.

Keep route registration in `src/router.js` aligned with new pages and layouts. Do not edit `dist/`; it is generated by the build.

## Build, Test, and Development Commands

- `npm install` installs dependencies.
- `npm run dev` starts the Vite development server with hot module replacement.
- `npm run build` creates the production bundle in `dist/`.
- `npm run preview` serves the built bundle locally.
- `npm run lint` runs ESLint across JavaScript and JSX files.

Run `npm run lint` and `npm run build` before handing off a change. There is currently no automated test runner configured.

## Coding Style & Naming Conventions

Use ES modules and JSX. Follow the surrounding file’s formatting, including its indentation and quote style; do not reformat unrelated code. Name React components and page files in PascalCase (`CartPage.jsx`), hooks with a `use` prefix, and general utilities in camelCase. Keep feature-specific code under its feature directory and prefer shared primitives over duplicated controls.

ESLint enforces recommended JavaScript rules plus React Hooks and Vite refresh rules. Address lint errors rather than disabling rules unless a documented exception is necessary.

## Testing Guidelines

No testing framework or coverage threshold is configured. For each change, manually exercise the affected route with `npm run dev`, then run lint and a production build. If a test setup is introduced, colocate tests with the code they cover and use clear names such as `CartPage.test.jsx`.

## Development Workflow

- `main` is the live production branch. Code on this branch is deployed for real users.
- `develop` contains the latest integrated work from all developers for shared testing.
- `staging` mirrors Production as closely as possible and is used by QA, testers, and business stakeholders for final validation before release.
- Name working branches with Conventional Commits / GitFlow prefixes followed by a descriptive task name: `feat/<task-name>`, `fix/<task-name>`, `hotfix/<task-name>`, `refactor/<task-name>`, or `chore/<task-name>`.

## Commit & Pull Request Guidelines

Git history is unavailable in this checkout, so use concise imperative commits, such as `feat: add product filters` or `fix: handle empty cart`. Keep commits focused. Pull requests should explain the user-visible change, identify affected routes, link related issues when available, and include screenshots for visual updates. Note the validation commands run and any follow-up work.
